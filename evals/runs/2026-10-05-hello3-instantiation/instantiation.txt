## Move 1 — Instantiate

**What the change does.** `internal/handlers/hello_service.go` now trims `req.GetName()` and returns `status.Error(codes.InvalidArgument, "name is required")` when the result is empty; previously that input returned `HelloResponse{Message: "hello "}` with `nil` error. The unit test that asserted `"" → "hello "` was deleted and replaced with one asserting `InvalidArgument` for `" "`. The proto (`proto/hello/v1/hello.proto`) is unchanged: `HelloRequest.name` is a plain `string` with no `required`/validation annotation, so the contract file still says an empty name is a legal request — only the handler's answer to it changed. This is a semantic change to an existing method behind an unchanged contract.

**Worst case, concretely.** `hello` runs in exactly one cluster, `e1-dev` (`fleet` → single cluster `e1-dev`, env dev), one ready pod (`instances` → `{cluster=e1-dev} 1`), ClusterIP only, no external exposure (`exposure` → `type=ClusterIP` for `hello` and `hello-canary`). One caller is measured: `traffic` in namespace `frontend` under `spiffe://cluster.local/ns/frontend/sa/frontend`, ~0.5–1.16 rps (`callers`, `rps`). So the blast radius today is: every `hello.v1.HelloService/Hello` call that carries an empty or whitespace-only name starts failing with `InvalidArgument`, for that one caller, in dev. The prod overlay (`deploy/envs/prod/kustomization.yaml`, replicas 3, max 10) exists and `.github/workflows/promote.yaml` moves a tested digest onward, so the same behaviour is one promotion away from a 3-replica environment with no staging to catch it (`answers.staging_exists: no`).

**What makes this more than a one-line logic tweak — three things to check hard.**

1. *The repository's own probe calls `Hello` with an empty request.* `e2e/probe/main.go` invokes `cc.Invoke(ctx, *method, &emptypb.Empty{}, &emptypb.Empty{}, …)` — an all-default `HelloRequest`, i.e. `name=""`. Every e2e assertion against `Hello` (`e2e/run.sh:339`, `:359`) therefore now exercises the rejected path. The assertions are code-class based: `reach` is `[[ "$2" == CODE* && ! "$2" =~ (PermissionDenied|Unavailable|DeadlineExceeded) ]]` (`e2e/run.sh:227`) and the loop's `failure` set is `Unavailable, DeadlineExceeded, Internal, Unknown, Canceled` (`e2e/probe/main.go`). `InvalidArgument` is in neither, so e2e goes green while no longer proving the service ever answers successfully.
2. *The canary analysis is blind to this error class.* `deploy/base/rollout.yaml` `AnalysisTemplate server-errors` queries `code=~"Unknown|Internal|DataLoss|DeadlineExceeded"`. `InvalidArgument` is excluded by construction, so a 100%-`InvalidArgument` canary passes `successCondition` and promotes through 10% → 50% → 100%.
3. *And in the only environment that exists, the analysis is not even applied.* `deploy/envs/dev/kustomization.yaml` patches `/spec/strategy/canary/steps` to `[]` and removes `/spec/strategy/canary/analysis`. Dev is a straight replacement of the single replica. Combined with `alerts` → no data and the stack note "no alerting rules", and with Istio reporting gRPC errors as HTTP `200` (`rps` → `response_code=200`), a total failure of this method in dev would show only in `vikrant_rpcs_handled_total{code="InvalidArgument"}`, which nothing watches.

**The unknown that decides severity:** whether the deployed caller sends blank names. `callers` names the workload `traffic` in ns `frontend`; the repository does not contain it. If that generator (or the real `smallStepGiantLeap/frontend`) passes an unvalidated or absent name, this change turns a 100%-OK path into a 100%-error path at the moment of sync. That is the one fact worth delegating for.

**Properties this change cannot open:** within-budget (no new call, no fan-out; the error path returns *earlier*, doing strictly less work), available (no manifest, no lifecycle, no resource change), secure (no new path, no new grant; the error string is a constant and does not echo the input). Each still gets a one-line obligation to show it.

### Obligations

- **correct** — Establish that the proto is the contract of record and carries no validation that makes an empty name already illegal, and that rejecting it does not contradict a documented decision: read `proto/hello/v1/hello.proto` (`HelloRequest.name = 1`, no options) and `README.md`. Then establish the PR description matches the diff — it says "trim and refuse"; the diff *also* deletes the only test pinning the old behaviour, which the description does not mention. Failure to establish: warning.
- **correct** — Establish whether the deployed caller `traffic` (ns `frontend`, SA `frontend`, per `callers`) and the real `smallStepGiantLeap/frontend` send a name that can be empty or whitespace. Delegate to **org-finder**: find the repo/manifest that builds the `traffic` workload and the `frontend` caller of `hello.v1.HelloService/Hello`, and report the request it constructs and how it handles a non-OK code. If it sends an empty name, this is a live break of a working path: blocking. If it always sends a non-empty name: info.
- **reversible** — Establish that during the canary (prod) or the straight replacement (dev) the same input gets two different answers, and that rollback is clean: no stored data, no schema, no config format (diff touches only `internal/handlers/`). Also establish that no caller treats the greeting response as a required field it cannot handle the absence of. Evidence: the diff; `deploy/base/rollout.yaml` canary steps; the caller repo found by org-finder. Mixed-version inconsistency with a clean code-only rollback: warning. A caller that breaks irrecoverably: blocking.
- **progressively-delivered** — Establish that the environment's paved road (Argo Rollouts canary + `server-errors` AnalysisTemplate, Argo CD GitOps — stack `deploy`, verified by `owner` → `owner_kind=Rollout`) would *not* catch this failure: the analysis query at `deploy/base/rollout.yaml` (`code=~"Unknown|Internal|DataLoss|DeadlineExceeded"`) excludes `InvalidArgument`, and `deploy/envs/dev/kustomization.yaml` removes steps and analysis entirely for the only live cluster. Evidence: those two files plus `owner`/`instances`. A behaviour change that can error on existing input, delivered with no judging gate in the only environment it reaches: warning (dev-only, 1 pod, 1 internal caller) — blocking if org-finder shows the deployed caller sends blank names, since then the rollout promotes a total outage for that caller.
- **observable** — Establish that a 100%-`InvalidArgument` outcome is visible to an operator: `vikrant_rpcs_handled_total` carries a `code` label (`internal/platform/metrics/metrics.go:52`; `errors` query uses it) so the signal exists, but `alerts` returns no data and the stack states "no alerting rules", and Istio reports gRPC failures as `response_code=200` (`rps`), so the mesh-side view stays green. Establish also that there is no flag or config that disables the new rejection without a deploy (grep `internal/` for any feature-flag or env-var gate). Signal present but nothing watching it, no off switch: warning.
- **stable-under-failure** — Establish that the new error code cannot be amplified into a retry storm: `deploy/base/mesh/virtual-service.yaml` retries on `connect-failure,refused-stream,unavailable` only, so `InvalidArgument` is not retried by the mesh; confirm the caller found by org-finder does not retry non-retryable codes itself. Also confirm `destination-rules.yaml` outlier detection (`consecutive5xxErrors: 0`) does not eject pods on gRPC `InvalidArgument`. No amplification: info. A client-side retry loop on `InvalidArgument`: warning.
- **proven** — Establish what would have caught this being wrong. Two concrete gaps to confirm: (a) the deleted map entry `"": "hello "` was the only unit test of the previously-supported input, and no test now asserts the behaviour for a caller that legitimately sends no name; (b) `e2e/run.sh:339` and `:359` call `Hello` through `e2e/probe/main.go`, which sends `emptypb.Empty{}` (name=""), so after this change the e2e suite's only `Hello` calls hit the rejection path, and its `reach`/`no-errors` predicates (`run.sh:227`, probe `failure` list) accept `InvalidArgument` — the suite cannot distinguish a working service from one that rejects everything. Confirm `make test` and `e2e/run.sh` both pass on this head (CI `.github/workflows/ci.yaml` jobs `test`, `e2e`). E2E that no longer exercises a successful `Hello`: warning; blocking if the deployed caller sends blank names, because then correctness rests entirely on an untested-and-unasserted path.
- **within-budget** — Show why it is unaffected: no new dependency call, no fan-out, and the rejection returns before `greeting()`, so per-request work only decreases (diff in `hello_service.go`); `inflight` is 0 and `ceiling` is 2 in `e1-dev`.
- **available** — Show why it is unaffected: the diff touches no manifest, probe, resource limit, PDB or lifecycle (`pdb` → 1 expected pod, `restarts` → 0, unchanged by this PR); no PSS-restricted surface is touched.
- **secure** — Show why it is unaffected: no new network path, identity, secret or permission; the returned message is the constant `"name is required"` and does not echo caller input; mTLS and the `authz-allow-frontend` policy are untouched by the diff. (The standing `denials` → 750 count is from the e2e/authz fixtures, not this change.)
