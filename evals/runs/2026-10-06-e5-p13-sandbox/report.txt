Because the client spawns a fresh grpcurl process per iteration with -plaintext, each call is a new TCP + HTTP/2 connection, so the appliance sees up to 10x the connection churn, not merely 10x the requests on an established connection. If the server or the appliance cannot carry it, the failure is not confined to this client: every other workload routed through api.e5.internal degrades, in the e5-server cluster. Both clusters are dev (fleet: e5-client, e5-server both env=dev), which caps user impact, but the change's entire purpose is to raise load on a shared dependency whose capacity is nowhere stated in this repository (README.md defers it: 'how that name reaches the server is the platform's business').
